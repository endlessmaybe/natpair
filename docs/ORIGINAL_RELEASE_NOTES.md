# NATPair v1.2.0：全员互连 / Minecraft Java 星形房间

> 这是 2026-10-08 原始交付说明。GitHub 公开包改用配置模板，不提供当时交付中的私人服务器配置。当前下载与配置步骤见 [使用说明](USER_GUIDE.md)。

本版单列 **MC 星形房间（Tailscale 接入）** 模式。一人选择房主，其余选择玩家；只为房主与各玩家建立辅助通道，玩家之间不做辅助探测。最多 8 人含房主，8 人时只需 7 条房主连接。已有原生 IPv6 / IPv4 直连的房主连接自动跳过辅助扫描。原来的全员互连模式仍可选择。

## Minecraft Java 使用步骤

1. 每人完整解压新版到新文件夹，先登录同一个获授权的 Tailscale 网络，以管理员身份运行 NATPairMesh.exe。
2. 房主先启动 Java 服务端，或进入游戏世界选择“开放到局域网”。**服务端默认端口常为 25565；开放到局域网要使用游戏当次显示的端口，不能直接照抄 25565。** 房主选择“MC 星形房间（Tailscale 接入）”、角色“房主”，填写实际游戏端口。
3. 房主生成房间码并加入；其他人选择同一个 MC 星形模式、角色“玩家”，输入同一码加入。玩家输入框中的端口不决定游戏地址，所有人自动使用房主公布的端口。同一房间不允许两个房主，也不能混用星形和全员互连模式。
4. 下方“MC 直连地址”显示房主的 `100.x.x.x:游戏端口`，点击“复制地址”，在 Minecraft Java 的“多人游戏 → 直接连接”中粘贴。
5. 玩家可以先进入房间等待房主。房主退出后玩家留在房间等待；新房主可以在原房主明确退出后加入。修改房主角色或游戏端口时，先停止退出，再改设置重新加入。

地址公布代表已经获知游戏目标。是否辅助直连成功以成员表的真实验证状态为准；等待辅助打洞时，Tailscale 本身已可用的路径仍能承载游戏。房主需要保持游戏、Tailscale 和辅助程序运行。MC 服务要监听允许远程接入的地址，并获得自己的游戏入站许可；本软件添加的是自身和 Tailscale UDP 通道的许可，不会替你启动 MC 或开放任意游戏端口。

Java 游戏 TCP 连接通过 Tailscale 的 UDP 隧道传输；没有恢复独立公网 TCP 打洞，也不需要等它成功。星形指本软件的辅助配对与调度，不改变 Tailscale 自身的授权或底层网络拓扑，不会让房主转发玩家之间的任意业务。

## 修复预算用满后的停滞

共存档达到新增预算后，保留新候选的位置，最多以 20 包/秒复测最近成功发送过的一小批候选，每对池最多 128 个。仅在本对具有有效探测轮次时执行；不用遍历全部已发组合反复刷新。这样其余近期记录能正常过期，随后继续新增扫描。记录过期是软件预算估计，不代表读取到了运营商映射表或确认该映射已释放。没有有效旧候选时继续等待预算恢复。

界面和日志分别显示等待房间心跳、等待本对轮次、双方准备、业务让行与预算恢复倒计时。只剩一对待连且双方心跳新鲜时，协调服务续期原探测任务，不每两分钟丢弃任务重新准备。多人仍轮转公平分配，已通通道继续维护。

新增默认“Bifrost 共存”档位：扫描发送摊匀，最多积攒两个发送令牌；新增组合和近期组合占用分别设预算；日志中的新健康异常只作为补充降速信号。所有成员对共享同一预算。停止重新加入时，同一程序保留最近的组合记录，避免立即把预算归零后再次突发。保留上一版 Tailscale 身份同步修复。

1000 是扫描包速度上限，并不保证持续发满；已有连接保活、认证回包、协调和业务优先处理，另计。此模式不修改或重启 Bifrost，不关闭它的安全检查。无法保证代理永远不断，也不能把“曾达到 3000”理解成稳定安全限额。

全员互连模式最多 8 人，8 人时有 28 对成员关系；MC 星形模式同样最多 8 人，但只有 7 对房主—玩家关系。程序逐对尝试建立辅助 IPv4 UDP 通道，打通一对就立即使用，其余继续排队探测。

## 开始使用

1. 所有人完整解压同一个新版压缩包到各自的新文件夹，保留 `NATPairMesh.exe`、`config.json` 和整个 `_internal`。不要只发 EXE。
2. 接入 Tailscale 时，所有人先登录同一个已授权的 Tailscale 网络，再右键 `NATPairMesh.exe`，选择“以管理员身份运行”。
3. 选择“接入 Tailscale（全员互连）”。一个人生成房间码并发给其他人，所有人填写同一码和各自昵称，点击“加入房间 / 开始”。
4. 新版自动交换各自的 Tailscale 地址和节点信息，逐对核对节点，无需手动选择七个对方地址。
5. 只想看 UDP 打洞时，选择“仅 UDP 打洞（不接入 Tailscale）”。该模式无需 Tailscale 登录，不创建 Tailscale 代理；没有管理员权限时，也不会自动添加 Windows 入站许可。

这一版使用独立的新协调服务，压缩包内已经配好；请所有成员使用 v1.2.0 完整配置。旧版本服务保留，但旧配置不支持新 MC 星形房间。

## 三个探测档位

- **Bifrost 共存：平滑探测，最高1000包/秒**：默认档位。所有成员对合计的扫描包按时间摊匀，空闲后最多补发两个。默认新增速度最高 200 组合/秒，滚动 15 秒内最多新增 900 组合；记录最近 180 秒触达的组合，参考预算为 2400 个。重复触达会更新最近触达时间，不能用重复包把旧组合伪装成已经释放。达到预算时保留当前扫描位置，有效轮次内复测一小批已有候选并等待其他记录过期，已通连接仍继续保活与传输。**180 秒和 2400 都是保护参数，不是读取到的真实 NAT 生存期或运营商/Bifrost容量。** 本程序不能看到其他应用产生的映射，也不能保证这些数值适合每条网络。双方都与 Bifrost 共用时，双方均选这个档位。不会为了显示 1000 而补发无用包。

- **不限额：有效连续探测**：探测包和新增探测组合都没有固定的软件额度上限。每台电脑同时集中探测一对，先处理业务、认证回包和保活；已有业务队列等待处理时，新探测让出执行机会。打通之后停止该对的广泛扫描，保留原来的命中套接字。
- **新增组合：1000/秒（全机共享）**：所有成员对、所有本机探测套接字合计，滚动一秒最多 1000 个首次发送成功的探测组合。组合是“本机 UDP 源端口 × 对方 IPv4 × 对方目标端口”。已有组合的重发、认证回包、协调信息和业务数据不扣新增额度。不会按七个人各给 1000。

不限额不意味着运营商 NAT、路由器或网卡也没有容量上限。大量新增映射仍可能影响已建立连接；程序的调度与保活能降低干扰，不能消除上游资源耗尽的可能。需要与 Bifrost 共用时可在停止、清理完成后选择共存档；原来的“新增组合1000”档仍允许重发不限额，不具备共存保护。

这三个档位调整的是探测。UDP 隧道业务队列与吞吐处理沿用已有双人核心，并不因选择不限额而改成无限队列。

## 界面怎么看

房间人数含自己。短暂失联的成员会保留席位，明确停止退出会及时移除。房间只有自己时一直等人，不会 30 秒自动结束。

每个成员单独显示连接方式：

- **原生 IPv6 / IPv4 直连**：已取得 Tailscale 真实数据回应及对应端点，跳过这对的辅助扫描。
- **NATPair UDP 直连 · Tailscale 已验证**：外层 UDP 有认证往返，并取得所选本地代理上的 Tailscale 数据验证。
- **UDP 已验证 · 等待 Tailscale 数据确认**：外层打洞成功，但尚没有足够证据证明 Tailscale 已使用辅助通道。
- **Tailscale 已可用，代理路径核实中 / 经 DERP，代理待选用**：Tailscale 已有真实数据回应；不会因辅助代理证据尚不完整而说整个 Tailscale 没连上。
- **双方准备 / 等待轮次**：正在交换本轮信息，或者其他成员对正在集中探测。
- **业务传输优先，探测让行**：已有通道的业务待处理，探测暂时让行。

“实发 / 新增（秒）”是近 10 秒实际探测发送速率与首次成功探测组合速率，不是名义上限；观测服务器的报文和认证回包不算进新增探测组合。下方也显示全机新增速率和累计数量。

“首次 UDP 用时”从本机加入这一轮房间开始计算，包含排队等待。完整记录另存每对成员自己的准备、有效探测和首次成功时间，不会用只算有效探测的几秒来掩盖排队时间。

## 稳定性处理

每对成员有独立的源套接字、探测身份、会话、扫描进度、认证密钥和本地代理。一个人退出或重进，只替换相关的成员对；其他已通成员继续使用。

所有成员对共用一个加密 UDP 协调套接字；Tailscale 元数据查询与发现监听由本机共享。发现报文按完整目标 IPv4 与端口分配；若该地址同时属于多个节点，就丢弃这条无法唯一归属的副本，等待新的候选，不广播给其他成员。

已有认证通道不会仅因房间信息暂时缺失而被销毁。明确退出按本轮身份处理；真正失去认证回包的那一对自行恢复。旧会话的延迟报文不会重新占据房间。停止会等待本轮线程与资源清理完成，之后可在同一窗口重新加入。

本版不加入防抖动缓冲、不恢复公网 TCP 独立打洞。TCP 业务继续通过 Tailscale 的 UDP 数据通道承载。尚未打通的成员对可继续使用 Tailscale 自己可用的中继路径；本程序不让其他成员替你转发业务。

## 记录与验证范围

每对首次认证成功自动保存证据，不需要记得立即导出。记录在程序目录的 `packet-logs` 下；“导出完整记录”会生成 `NATPair-Mesh-test.zip`，包含房间概况、各对状态和轮转后的报文元数据。对方退出后也保留该对曾经成功的统计，最近 56 个已结束成员对在汇总中，另外各对的结束记录会保存到磁盘。每对一般保留最近四段报文日志，每段约 4 MiB，另保留首次成功证据和开场交换；不能把轮转后的导出视为无限期保存的所有历史包。

发布前完整 118 项回归测试通过，包含原全员互连的八人 28 对真实 UDP 通道和四人星形的三条房主认证通道。星形测试覆盖房主与玩家退出重进、无房主等待、拒绝重复房主、原生 IPv6 跳过和两个辅助代理隔离。另有实际 Windows EXE 的三人星形测试、原生 Tailscale 身份读取和自有公网服务器星形连接检查。

多人代理隔离测试使用真实 UDP 和 AEAD 传输、合成的原生 Tailscale 报文，不是三台真实 Windows 的原生 Tailscale 认证测试。公网服务器测试也不等同于两端都是 NAT4。本版保留以前成功的双人打洞核心，但不能据此承诺八名不同运营商用户的所有 28 对都能直接打通，或者保证长期网络资源永不耗尽。

多人房间不会扩大 Tailscale 账户自身的人数或设备授权额度。纯 UDP 模式也不是一个独立的虚拟网卡 VPN。


## 共存档位的补充恢复

程序只读取 Bifrost 健康日志，不发送 Bifrost 控制命令。读取不到日志时，主动的平滑发送和组合预算仍然生效，界面明确提示日志不可读。启动时旧日志不被当作新的故障。新的节点健康异常将扫描上限暂时降为 250 包/秒、新增最高 50/秒；新的数据通道检查失败还会暂缓新增 10 秒。没有后续异常时 15 秒后恢复原档位，始终不拆掉房间、命中套接字或已验证通道。该日志反应不能代替提前限制突发，所以两者同时使用。

预算只覆盖本程序记录的 UDP 发送，不是整台电脑或 ISP 的完整流量。多人共用预算是同一程序内的成员对共用，多个独立 EXE 进程不能共同保证这个上限。彻底退出再启动程序也无法读取 ISP 仍保留的映射，不应反复重启来追求清零。导出记录附带 `coexist_guard`、实际探测包速率、实际新增速率、最近触达组合数量和保护原因。

CLI 使用 `--coexist` 启用新档位。`--new-combinations-per-second 1000` 是原来的新增限额档。未指定两者时 CLI 保留原始不限额行为。

CLI 星形模式增加 `--star-role host` 或 `--star-role player`，房主可指定 `--game-port 41234`。默认接入 Tailscale；`--udp-only` 仅供打洞验证，不构成 MC 游戏接入。GUI 中 MC 星形始终接入 Tailscale。
